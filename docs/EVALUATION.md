# 首轮试验结果：2026-10-04

受限原型已跑通 Markdown、Hermes、Codex 三类资料的采集、提炼、来源查询和恢复。样本很小，尚不足以证明长期自动运行的准确性或稳定性。当前适合继续做受控接入试验。

## 范围和版本

- 虚构中文资料：8 条来源、22 条提炼记忆；11 道有依据的问题与 1 道未知问题。
- 私有资料：3 篇 Markdown、2 段 Hermes 对话、1 段 Codex 对话，共 6 条来源、44 条后端记忆。发现并在查询层排除 1 条不受原文支持的推断。
- Windows / Python 3.13；Hindsight 0.10.2；PostgreSQL 18.1.0；FastMCP 4.0.10。
- 本地向量使用 multilingual-e5-small；日常查询不调用付费 LLM，不启用 Reflect 或自动 Consolidation。
- 检索先取 Hindsight 候选，再按其多语言语义分数排序，最多回传 4 条记忆。排序仍是试验策略。

## 检索结果

下表统计“预期来源是否命中”，不是最终答案正确率，也不能证明记忆的每个字都准确。未知题不计入分母。

| 资料 | 候选检索预算 | 首条来源命中 | 前四条来源命中 |
|---|---:|---:|---:|
| 虚构中文 | 512 | 11/11 | 11/11 |
| 虚构中文 | 1024 | 11/11 | 11/11 |
| 私有小样本 | 512 | 1/6 | 2/6 |
| 私有小样本 | 1024 | 6/6 | 6/6 |

恢复数据库后重测仍得到上述命中结果；暖缓存下查询中位延迟约 35–40 ms。该数据不含主聊天模型生成答复、网络访问、首次加载模型和更大语料的开销。

因此暂用 1024 作为默认候选预算，再返回少量来源可核对的记忆。预算主要控制后端候选内容，不是 MCP 整个 JSON 的精确 token 上限；来源 ID、工具描述和元数据也会消耗客户端 token。实测两个工具的 schema JSON 为 969 bytes，bytes 不能直接换算成 token。

未知护照问题仍会检索到其他相关个人资料。当前接口明确提醒“检索结果不证明问题已回答”，但本轮没有验证主聊天模型一定会拒绝编造。不能将来源命中率用作未知题拒答率。

## 提炼质量与模型选择

Pro 的首轮虚构提炼中，报告的 reasoning 占输出约 82%。4096 的输出上限在真实工程对话上触发截断、拆段重做和超时，节省上限反而增加总消耗。修正为 8192、异步 operation，并关闭模型和 worker 自动重试。

直接关闭 Pro 推理的简短 JSON 试验，将“助手宣称已部署成功”错误输出为已验证成功。这种简单提炼方式未通过验收。

随后在实际 Hindsight 提炼流程中，用独立虚构资料检查 Flash 配置，检查机器归属、未知原因、助手宣称、咖啡否定和偏好更新时间，边界保留正确；再对两段真实 Hermes 对话提炼。Flash 配置显式请求关闭 thinking，但其返回 usage 未提供单独 reasoning 明细，不能仅据此宣称推理用量为零。

真实资料复核发现一条“报告未列出某些内容”的推断，与原文列出的内容不符。已保存排除原因，按来源版本隔离该记忆；MCP 和 CLI 查询使用相同排除机制。其他工程状态仍应理解为来源对话中的陈述，不能因为进入知识库就升格为独立核实结果。

Flash 是后续提炼试验的候选；这轮结果尚不能证明它可无审核处理全部生活、工作或高风险资料。任务 Runbook 的临时要求也会产生冗余记忆，长期价值筛选仍需改进。

## 2026-10-04 Linux 部署验证

在独立 Ubuntu 24.04 / 2 vCPU / 4 GB 宿主安装 PostgreSQL 18、pgvector 和 Hindsight 0.10.2，把既有数据库、6 条真实来源、纠错记录及累计费用账本迁移过去。使用已缓存的中文向量模型，HTTP 只监听 loopback，跨机器通过受限 SSH stdio 接入。数据库应用角色已撤销超级用户、建库和建角色权限。

- Windows 经实际 SSH MCP JSON-RPC 测试两个工具：6/6 预期来源进入返回的前四条，所有来源可打开。包括来源读取的暖查询约 0.09–0.13 秒，首个查询约 0.36 秒。这仍是来源命中，不能当作最终回答准确率。
- 本机安装的原生 Codex 二进制在独立 stdio app-server 中，通过 `mcpServerStatus/list` 连接并发现 `memory_search`、`memory_source`，工具目录没有错误。这次检查未创建聊天或启动模型请求；老对话仍需重新载入，主模型是否会主动选择查询尚未验证。
- Hermes 使用实际安装的 MCP SDK 调用两个工具，再通过自己的工具注册模块注册成功，命名为 `mcp__personal_memory__memory_search` / `memory_source`。发现现有 `hermes-cli` 工具集不包含新 MCP，保留原工具集并加入 `mcp-personal_memory` 后，实际模型工具构建器中两工具可见。网关已重新载入配置；没有向聊天平台发送测试消息，因此真实主聊天模型何时选择查询尚未验证。
- Windows 已登记登录后运行的隐藏采集任务；来源拉取为 Linux timer；提炼 worker 单次最多处理一条、每 30 分钟执行一批，启动前等待 API 就绪。历史不全量回填。仅启用之后的新会话以及少量笔记白名单参与这一批。
- 来源传输有独立变更日志、确认游标和批次上限。新增测试覆盖 131 条记录分页、确认丢失重放、来源库重建检测和未变化文件跳过解析；26 项测试通过。连续空采集未新增模型请求。随后把这次实际工作的验证记录保存到 Obsidian，经已配置的采集服务导入、同一 worker 提炼，来源档案增为 7 条、pending=0，新增七条记忆逐条复核未发现无依据补写。查询新宿主方案时，新记录的具体宿主与软件事实进入前四条。尚未收到启用后的真实完整新会话，聊天新资料仍需实际观察。
- 在独立虚构 bank 验证新宿主实际模型调用，约 6.09 秒提炼出三条记忆，正确保留“助手声称，是否成功未知”和“项目临时预算，非永久偏好”。新增一次付费请求估算 0.008973 元。
- 新增真实工作记录提炼一次，估算 0.017844 元。费用上限仍为 200 元；本阶段明确增加最多 20 次尝试，累计请求上限为 50，未清空先前费用。当前 32 次请求，已知用量估算 1.436616 元，四次未知请求保留 1.592541 元，合计 3.029157 元。还未核对供应商真实账单。
- 发现旧 Windows 试验遗留一条 `reserved`：核对原试验已停、后端没有未完成操作后，将其按原预留金额转为未知费用并记录原因；没有释放额度。
- 新宿主再次做完整 PostgreSQL dump，恢复到全新隔离数据库，25 张表的行数和内容指纹均一致；保留来源/费用 SQLite 副本和 SHA-256 清单。每日备份已启用，未来定时执行效果还需观察。

当前 API 进程组约占 1.3 GB，数据库池上限设为 8；该资源数字仅适用于此小样本。读取失败、提炼失败、原文消失、来源游标损坏、网页 AI 接入及更大语料的长期质量仍需后续验收。上述验证在首次公开 Alpha 发布前完成；公开版本以 GitHub 标签和发布记录为准。
